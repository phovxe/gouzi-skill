# Landing Page 文案框架选择器

来源：[BigFive - The 15 best copywriting frameworks to make your landing pages more effective](https://bigfive.it/en/20-copywriting-frameworks-to-create-landing-pages-that-sell/)

本文页面标题称 15 个框架，但正文实际列出 14 个。以下只保留可直接用于 landing page 审计、重排和改写的规则，并加入适用边界。

## 目录

1. 组合原则
2. 框架选择表
3. 14 个框架
4. 真实性与测试边界

## 1. 组合原则

- 默认用 **AIDA** 组织整页递进。
- 根据页面最主要的说服任务，选择一个主叙事框架；不要平均使用所有框架。
- 把局部框架嵌入 AIDA：4U 检查首屏，PAS 描述痛点，FAB 翻译特性，STAR 写案例，PPPP/AAPPA 组织证据，CTA 完成行动。
- 每个区块只解决一个主要用户问题，并自然引出下一步。
- 先确认受众认知阶段、购买风险、产品复杂度和证据类型，再选框架。

## 2. 框架选择表

| 页面任务 | 优先框架 | 选择理由 |
| --- | --- | --- |
| 通用整页转化 | AIDA | 从注意到行动的完整主链 |
| 高痛点、强问题意识 | PAS | 快速聚焦问题、后果和解决方案 |
| 技术产品、参数密集 | FAB | 把特性翻译成优势和用户收益 |
| 强转型结果 | BAB | 清楚呈现现状、目标状态和桥梁 |
| 需要承诺与证据 | PPPP / AAPPA | 让承诺、证明和行动紧密相连 |
| 已有注意、但信任不足 | IDCA | 在兴趣与行动之间加入确信 |
| 新品类或复杂服务 | ACCA | 先教育理解，再建立确信 |
| 客户案例 | STAR | 用情境、任务、行动、结果呈现事实 |
| 复杂 B2B 决策 | SCIPAB | 展开情境、影响、方案、行动和收益 |
| 故事驱动的转型 | PASTOR | 用真实故事连接问题、变化与方案 |
| 简短、直接的交易页 | SLAP | 缩短从停止浏览到购买的路径 |
| 渠道到复购的全生命周期 | RACE | 检查流量、互动、转化与持续经营 |
| 标题与钩子质检 | 4U | 检查独特、有用、具体和真实时机 |

## 3. 14 个框架

### AIDA：Attention, Interest, Desire, Action

- **Attention**：用标题、视觉和关键词吸引注意。
- **Interest**：展示独特优势和与用户相关的价值。
- **Desire**：说明如何解决问题或满足需求，让用户想拥有结果。
- **Action**：用明确 CTA 引导购买、咨询或获取更多信息。
- 用作整页默认主干；详细规则见 [laws-and-rules.md](laws-and-rules.md)。

### PAS：Problem, Agitate, Solve

- **Problem**：准确指出用户已经感受到的问题。
- **Agitate**：说明问题持续存在的代价、风险或负面体验。
- **Solve**：把产品/服务作为可信解决方案，并引出行动。
- 只放大真实后果；不要用恐吓、羞辱或虚构风险制造焦虑。

### FAB：Features, Advantages, Benefits

- **Features**：描述技术、功能或服务属性。
- **Advantages**：说明该属性相对替代方案带来的直接优势。
- **Benefits**：把优势翻译成用户能感知的结果、节省或改善。
- 每个关键特性都要能回答“所以这对用户有什么用”。删除无法连接到收益的参数堆砌。

### BAB：Before, After, Bridge

- **Before**：描述用户当前状态或问题。
- **After**：呈现理想结果和成功状态。
- **Bridge**：说明产品、流程或服务如何把用户从 Before 带到 After。
- 适合结果可视、差异明显的产品；桥梁必须具体，不能只写“选择我们”。

### PPPP：Picture, Promise, Prove, Push

- **Picture**：用清晰视觉或场景让用户看见产品、问题或理想状态。
- **Promise**：说出最主要、最相关的结果承诺。
- **Prove**：用评价、案例、统计、演示或可验证事实证明承诺。
- **Push**：在承诺已被证明后推动明确行动。
- 让证据与承诺一一对应；不要用无关认证替代结果证据。

### IDCA：Interest, Desire, Conviction, Action

- **Interest**：用与需求直接相关的价值进入主题。
- **Desire**：展示满足需求后的结果。
- **Conviction**：用评价、案例、社会证明和演示建立确信。
- **Action**：给出清晰直接的 CTA。
- 适合流量已具备初步注意，但产品风险高、信任不足的页面。

### ACCA：Awareness, Comprehension, Conviction, Action

- **Awareness**：让用户意识到产品、问题或新机会。
- **Comprehension**：解释产品如何工作、为何有帮助。
- **Conviction**：用证据说明这是合适选择。
- **Action**：推动购买、预约或咨询。
- 适合新品类、复杂方案和需要教育市场的服务；不要过早跳到 CTA。

### STAR：Situation, Task, Action, Result

- **Situation**：交代客户背景、环境和限制。
- **Task**：说明必须完成的目标或挑战。
- **Action**：具体描述采取了什么措施。
- **Result**：给出可验证结果及时间范围。
- 用于案例区而非强行组织整页。结果必须真实；没有数据时使用可证实的定性结果并明确限制。

### SCIPAB：Situation, Complication, Implication, Position, Action, Benefit

- **Situation**：描述用户当前情境。
- **Complication**：指出阻碍与困难。
- **Implication**：解释不解决会造成的业务影响。
- **Position**：提出本方立场与解决方案。
- **Action**：说明如何实施或开始。
- **Benefit**：展示采用方案后得到的收益。
- 适合复杂 B2B、高客单和多决策者场景；保持层次简洁，避免把页面写成冗长报告。

### PASTOR：Problem, Amplify, Story, Transformation, Offer, Response

- **Problem**：确认受众问题。
- **Amplify**：说明问题的重要性和真实影响。
- **Story**：用真实人物或客户经历建立情境。
- **Transformation**：展示从问题到解决后的变化。
- **Offer**：提出清晰、具体、可交付的方案。
- **Response**：要求用户采取下一步行动。
- 适合故事和身份认同重要的页面；故事、变化和后果都必须可证实。

### SLAP：Stop, Look, Act, Purchase

- **Stop**：让用户停止滑动并聚焦产品。
- **Look**：帮助用户快速理解价值和相对优势。
- **Act**：推动低门槛动作，如试用、下载或咨询。
- **Purchase**：简化最终交易或预约流程。
- 明确 Act 是微转化还是最终购买，不要让中间动作成为无目的的线索收集。

### RACE：Reach, Act, Convert, Engage

- **Reach**：确认目标受众和最适合触达他们的渠道。
- **Act**：提供可参与、易理解的页面体验。
- **Convert**：把访问者转化为购买者或线索。
- **Engage**：在转化后通过有价值的沟通维持关系。
- RACE 更适合检查落地页的上下游：广告与页面是否匹配、提交后是否有跟进、是否只优化页面而忽略流量质量。

### AAPPA：Attention, Advantage, Evidence, Persuade, Action

- **Attention**：抓住注意。
- **Advantage**：展示与用户相关的优势。
- **Evidence**：用评论、比较、案例或结果证明有效。
- **Persuade**：把优势和证据连接到“为什么现在适合我”。
- **Action**：提供清晰、易用的按钮或表单。
- 适合优势需要证明的产品；Evidence 不能被泛泛的品牌口号替代。

### 4U：Unique, Useful, Ultra-specific, Urgent

- **Unique**：说清与替代方案真正不同的价值。
- **Useful**：让用户立即理解能解决什么问题或满足什么需求。
- **Ultra-specific**：使用具体对象、结果、条件和交付物，避免空泛形容词。
- **Urgent**：只呈现真实存在的截止时间、库存、名额、业务窗口或机会成本。
- 主要用作标题、钩子和 CTA 的质检表，不要求四项都被硬塞进一句话。

## 4. 真实性与测试边界

- 框架只定义表达顺序，不证明文案事实，也不保证转化提升。
- 不虚构评价、客户、统计数据、前后对比、权威背书、截止时间或库存。
- 不把“放大问题”变成操纵；使用与产品实际风险相称的语言。
- 对同一流量来源测试一个明确假设，保留主要指标和合格线索等护栏指标。
- 优先测试主框架、首屏承诺、证据类型或钩子，不同时重写所有变量。
